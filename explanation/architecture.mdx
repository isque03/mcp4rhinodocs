title: "Architecture"
description: "Why MCP4Rhino splits host, Tools, and Logic — and what that means for reloads."
---

MCP4Rhino is a Rhino 8 plugin that exposes modeling capabilities over a local MCP HTTP endpoint. The design keeps the host thin and puts most product surface in reloadable assemblies.

## The problem

Rhino plugins normally require a full restart to pick up code changes. Restarting Rhino for every tool tweak is slow for contributors and agents. At the same time, the HTTP listener, Rhino commands, and UI must stay stable while tools evolve.

A single monolithic `.rhp` would force restarts for every change and couple the network host to every geometry helper.

## The approach

```
AI client ──► mcp-remote / HTTP ──► MCP4Rhino host (.rhp)
                                        │
                                        ├─ HTTP listener (port 4010)
                                        ├─ Rhino commands + Status UI
                                        └─ ToolLoader ──► Tools + Logic (collectible ALC)
                                              │
                                              └─ RhinoCommon document ops (UI thread)
```

| Assembly | Role | Reload |
|----------|------|--------|
| Host (`MCP4Rhino`) | `.rhp`, HTTP listener, commands, Status dialog, RUI menu | Restart Rhino |
| Tools (`MCP4Rhino.Tools`) | MCP tool implementations | Hot-reload |
| Logic (`MCP4Rhino.Logic`) | Pure helpers used by Tools | Hot-reload with Tools |
| Contracts | Shared bridge interfaces | Usually with host |

Prefer new MCP capabilities in **Tools** (and **Logic** helpers). Keep the host thin.

Document and view mutations run on the UI thread so Rhino stays consistent.

## Trade-offs

- **Hot-reload speed vs host rigidity.** Tools iterate without restart; host/command/RUI changes still need install + restart.
- **Local-only by design.** Loopback MCP keeps modeling on your machine. Cross-machine use means you point the client at another host’s IP; there is no cloud collaboration layer in the plugin.
- **Client bridge required.** Most assistants use `npx mcp-remote` to speak MCP over stdio to the HTTP server. Native HTTP MCP is optional when the client supports it.

## Alternatives considered

- **All tools in the host** — simpler packaging, but every tool change forces a Rhino restart.
- **External process MCP server** — avoids plugin reloads, but loses tight RhinoCommon/UI-thread access and complicates install for end users.
